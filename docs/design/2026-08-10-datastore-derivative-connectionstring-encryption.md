# DataStoreDerivative Connection String Encryption

**Ticket:** [ADMINAPI-1482](https://edfi.atlassian.net/browse/ADMINAPI-1482)
**PR:** [#423](https://github.com/Ed-Fi-Alliance-OSS/ODS-Admin-API/pull/423)

> This is a condensed summary of the original design and implementation plan. The full documents (`docs/superpowers/specs/2026-08-10-datastore-derivative-connectionstring-encryption-design.md` and `docs/superpowers/plans/2026-08-10-datastore-derivative-connectionstring-encryption.md`) were removed from the repo for size; this file is the durable reference going forward.

## What it does

`DataStoreDerivative.ConnectionString` was stored unencrypted and returned in plaintext by Admin API V3, unlike the primary `DataStore` resource, which already encrypted it on write and never returned it. This brings `DataStoreDerivative` to parity with `DataStore`:

1. **Encrypts on write** — `POST /v3/dataStoreDerivatives` and `PUT /v3/dataStoreDerivatives/{id}` now encrypt `connectionString` via the existing `ISymmetricStringEncryptionProvider` singleton before persisting, mirroring `AddDataStore.Handle`/`EditDataStore.Handle` exactly (same DI shape, same `InvalidOperationException` on missing key, same encrypt-after-validate ordering).
2. **Never returns it** — `connectionString` is removed entirely from `DataStoreDerivativeModel` (and its mapper), matching the primary `DataStoreModel`, which never had the property. This single change fixes all three leak surfaces at once, since they share the one model/mapper:
   - `GET /v3/dataStoreDerivatives` (list)
   - `GET /v3/dataStoreDerivatives/{id}` (by id)
   - `GET /v3/dataStores/{id}` (detail — embeds derivatives via `DataStoreDetailModel.DataStoreDerivatives`)
3. **Backfills legacy plaintext rows lazily** — `DataStoreEncryptionHelper` gained `EncryptDerivativeConnectionStringsIfNeededAsync`, wired into all three queries that load `OdsInstanceDerivative` entities (`GetDataStoreQuery`, `GetDataStoreDerivativesQuery`, `GetDataStoreDerivativeByIdQuery`). A plaintext row is transparently re-encrypted and saved the next time it's read through any of those paths — no separate DB migration script.
4. **Manual test coverage** — `docs/http/dataStoreDerivatives.http` walks through create/read/update/delete against a live server, confirming `connectionString` never appears in any response.

## Design decisions

- **Scope: V3 only.** V2 has an equivalent `odsInstanceDerivatives` feature (`Application/EdFi.Ods.AdminApi/Features/OdsInstanceDerivative/`) with the identical plaintext-at-rest problem — confirmed its Add/Edit handlers call the command directly with no encryption, unlike V2's primary `OdsInstance`, which already encrypts and backfills. Fixing V2 was deferred rather than bundled in, because `AppSettings:AdminApiMode` serves exactly one of V1/V2/V3 per deployment, so a V3 deployment never exercises the V2 write path. **V2 derivative-encryption parity should be tracked as a follow-up ticket.**
- **Lazy backfill, not a migration script.** DbUp migration scripts are plain SQL with no access to the encryption key/provider, and the codebase already had working precedent for this exact problem on the primary `DataStore` (`DataStoreEncryptionHelper.EncryptConnectionStringsIfNeededAsync`, called from `GetDataStoreQuery`/`GetDataStoresQuery`). The derivative helper method was initially an intentional verbatim structural mirror of that method (same skip conditions: empty, already-encrypted, fails `ConnectionStringHelper.ValidateConnectionString`); two independent code reviewers flagged the duplication as a maintenance risk, so both methods were later deduplicated into one shared private generic helper. `OdsInstance`/`OdsInstanceDerivative` are defined in the external `EdFi.Suite3.Admin.DataAccess` package and can't be retrofitted to implement a shared interface, so the generic helper accesses `ConnectionString` structurally via `Func<T,string?>`/`Action<T,string>` delegates instead of a type constraint. Public method signatures are unchanged, so no caller or existing test needed updating.
- **Remove the property, don't null it out.** `DataStoreDerivativeModel` drops `ConnectionString` entirely rather than always mapping it to `null`, to match `DataStoreModel`'s shape exactly and avoid a residual field in the OpenAPI schema.
- **Constructor signature changes, not new abstractions.** `GetDataStoreDerivativesQuery` gained a third constructor param (`ISymmetricStringEncryptionProvider`, matching `GetDataStoresQuery`'s `(context, options, provider)` order); `GetDataStoreDerivativeByIdQuery` gained two (`ISymmetricStringEncryptionProvider`, `IOptions<AppSettings>`, matching `GetDataStoreQuery`'s `(context, provider, options)` order). Both resolve automatically via the app's reflection-based DI registration — no explicit registration changes needed.

## Implementation notes / known follow-ups

- **Collateral compile breaks found and fixed during implementation** (constructor/signature changes rippled beyond the plan's predicted file list): `EditDataStoreDerivativeTests.cs` (a validator test calling `Handle` with placeholder `null!` args), `DataStoreMapperTests.cs` (asserted the now-removed `ConnectionString` on an embedded derivative), and `Application/EdFi.Ods.AdminApi.V3.DBTests/Database/QueryTests/GetDataStoresDerivativeQueryTests.cs` (a DBTests file with a typo'd name — "DataStoresDerivative" vs "DataStoreDerivative" — that evaded an initial grep for callers).
- **A DBTests file intentionally skips the backfill**: `Testing.GetAppSettings()` leaves `EncryptionKey` unset, so `GetDataStoreDerivativeByIdQuery`'s backfill guard short-circuits and the pre-existing plaintext-equality assertion in that DBTest keeps holding — same no-op pattern already used by `GetDataStoresQuery`'s DBTests.
- **Bruno E2E schema cleanup was smaller than planned**: the plan listed 7 `.bru` files needing their stale `"connectionString"` schema assertion removed; 2 (`DataStores/GET - DataStores by ID.bru` and the multitenant equivalent) were found to already use a generic schema with no such assertion, so only 5 files actually needed edits. None of the 7 would have failed either way — none marked `connectionString` as `required` or set `additionalProperties: false`, so this was a documentation-accuracy cleanup, not a failing-test fix.
- **Final-review fix wave**: (1) a tautological FakeItEasy assertion in the two handler test files (`A<T>.That.Matches(...)` read the same mutated object it was asserting against, proving nothing about call-time ordering) was replaced with an `.Invokes(...)`-based capture that actually pins down encrypt-before-persist ordering; (2) a `CS8632` build break — `string?` locals added by that same fix without a `#nullable enable` directive — was caught by a full rebuild during branch-finishing (not by the fix's own scoped re-review, which trusted reported test output over an independent compile) and fixed in a follow-up commit.
- **Deferred, non-blocking test-coverage gaps** (noted by review, judged not worth the churn): the derivative helper's test suite covers 4 of the 8 skip-condition cases the sibling `OdsInstance` suite covers; no test asserts validate-before-encrypt ordering on `AddDataStoreDerivative` specifically (closed for both Add/Edit in the final fix wave); `GetDataStoreDerivativeByIdQuery`'s new test doesn't assert persistence back to the DB (unlike its `GetDataStoreQuery` sibling).
- **Operator note worth surfacing in release docs**: derivative connection strings created before this release remain plaintext at rest until each row is next read through a V3 GET. An operator can force convergence post-upgrade by paging `GET /v3/dataStoreDerivatives` once.
- **Post-merge review round 2 fixes**: (1) the two near-identical `DataStoreEncryptionHelper` methods were deduplicated into one shared private generic helper, accessed via `Func<T,string?>`/`Action<T,string>` delegates rather than a marker interface — `OdsInstance`/`OdsInstanceDerivative` are defined in the external `EdFi.Suite3.Admin.DataAccess` package and can't be retrofitted to implement one; public method signatures unchanged, no caller/test impact. (2) `GetDataStoreDerivativesQuery.Execute()` (parameterless) no longer runs the backfill — that overload has no client-facing caller (the real `GET /v3/dataStoreDerivatives` endpoint uses the `CommonQueryParams` overload); its only callers are `AddDataStoreDerivative`/`EditDataStoreDerivative`'s `BeUniqueCombinedKey` validator, so the backfill was adding an unscoped full-table encrypt scan to every derivative create/edit for a check unrelated to connection strings. `GetDataStoreQuery.Execute(id)`'s equivalent side effect (shared with 6 pre-existing validators and the real detail endpoint) was left alone as an already-accepted, bounded-scope pattern, but now has an explanatory code comment.
